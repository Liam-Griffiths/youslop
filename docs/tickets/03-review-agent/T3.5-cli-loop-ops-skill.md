## Goal
The whole production loop runs from a terminal with the app closed or open
(`new → plan → research → check → snapshot → review → fix → render --section
→ publish`), the HTTP handlers and the CLI share one body in `app/ops.py`,
and a Claude Code skill teaches the loop with doctrine numbers generated
from `FrameSpec` so they cannot drift.

## Why
This is the agent surface. Hyperframes is strong here (CLI plus skills); we
have most of the operations as HTTP handlers only.

## Read first
- `app/cli.py` (T0.7): the skeleton, `server.json` routing.
- `app/main.py`: handlers to factor: project create (grep `new_project`),
  the script generation job (`regenerate_script`); research currently lives inside `script_gen.brief`, not a standalone HTTP job, `start_render` ~2459,
  `youtube_upload` ~700; note each uses `with store.lock_for(pid)`.
- `app/jobs.py`: `start(kind, pid, fn)`; how progress is recorded; whether a
  job can be awaited in-process (add `wait(job_id)` if not).
- `app/check.py`, `app/review.py`, `app/storyboard.py`.
- `app/schema.py`: `FrameSpec` (T1.1) defaults.
- Hyperframes skill layout (`SKILL.md` + `references/*.md`) as a model; see
  `docs/roadmap.md` §4 row 3.5.

## Steps
1. `app/ops.py`: one function per operation, no FastAPI imports, each takes
   `(pid, payload, progress)` and returns a dict. Move bodies out of
   `main.py` handlers; handlers become thin: parse → `ops.x` → return.
   Start with: `create`, `plan`, `research`, `check`, `snapshot`, `review`,
   `fix`, `render` (`section=sid | full=True`), `publish`. Keep the HTTP
   paths and response shapes identical (the UI must not notice).
2. CLI subcommands map 1:1 onto `ops`. When `server.json` exists and the
   server answers `/api/health`, route through HTTP and poll the job;
   otherwise call synchronous ops in-process and block until completion (no `jobs.wait`).
   `render` without `--section` requires `--full --yes` and prints the
   memory/time note from the T0.8 constant first.
3. `cli doctrine` prints `FrameSpec` defaults as Markdown tables; `--write`
   regenerates `.claude/skills/corkbored-producer/references/motion.md` with
   a header "Generated by `cli doctrine --write`; do not edit".
4. `.claude/skills/corkbored-producer/SKILL.md`: when to use, the loop as
   numbered commands, the review rules (describe as a stranger, no score,
   fix order; review is targeted by default and `--full` only when asked), the preview rule (one section, cheap), and links to
   `references/motion.md` and `references/storyboard.md` (the patch schema,
   also generated from `storyboard.py` docstrings).
5. Tests: `ops` functions unit-tested with a temp data root for `create`,
   `check`; a CLI smoke test runs `cli list` and `cli doctrine` in a
   subprocess; a test asserts `motion.md` is in sync (`--write` to a temp
   file, compare).

## Implementer notes
*Added 2026-10-26.*

- **Make `ops` functions synchronous and let only HTTP use jobs.**
  `jobs.start` runs `fn(progress)` on a **daemon thread**; a CLI process
  would exit before it finishes. So:
  ```python
  # app/ops.py
  def plan(pid: str, payload: dict, progress) -> dict: ...   # blocks until done

  # app/main.py (thin)
  @app.post("/api/projects/{pid}/plan")
  def plan_route(pid: str, payload: dict = Body(default={})):
      _load(pid)                                   # 404 early, as today
      return {"job": jobs.start("plan", pid, lambda pr: ops.plan(pid, payload, pr))}

  # app/cli.py (in-process)
  ops.plan(args.pid, {}, progress=lambda m: print(m, flush=True))
  ```
  No `jobs.wait` needed.
- **Creation already generates the script and gathers media.** Preserve that HTTP behavior; `plan` maps to the resumable `/script` operation. Add an explicit `/research` operation for refreshing the dossier; it must not discard a completed script or its takes. CLI examples require an explicit project id after `new`.
- **There is no `/api/health`.** Add `GET /api/health` → `{"ok": true,
  "pid": os.getpid()}`. Token: the middleware `_require_token` (main.py
  ~63) lets **loopback** clients through without one, so a CLI talking to
  `127.0.0.1` needs no token. Send `x-vb-token: <token from server.json>`
  anyway (the header the middleware accepts), so it keeps working if the
  app is ever bound to another interface.
- HTTP polling: `GET /api/jobs/{jid}` (grep the route) until `state` is
  `done`/`error`, printing new `log` lines since the last poll.
- Move handlers one at a time and compare HTTP response shapes using mocked operations; manual UI clicks are an owner check when Chromium/loopback is unavailable. Do not move them all and test at the end. Suggested
  order (least to most coupled): `check`, `snapshot`, `review`, `create`,
  `plan`, `research`, `render`, `publish`. If the ticket grows past ~600
  lines, split at `render`/`publish` into T3.5b as README says.
- `render --section <sid>` = `render.preview_segment(project, sid)` (one
  segment, quarter size). `render --full --yes` = the existing full render
  job. Print the T0.8 note ("~N segments at a time, heavy on this machine")
  before starting.
- `cli doctrine` tables: iterate `dataclasses.fields(FrameSpec)` grouped by
  the comment headings in the class. Since comments are not introspectable,
  put the group in field metadata:
  `arrive_s: float = field(default=0.45, metadata={"group": "motion", "doc": "entrance length, expo.out"})`.
  Do that in T1.1 if it is not merged yet; otherwise add it here.
- The skill folder `.claude/skills/corkbored-producer/` is project-local;
  `SKILL.md` needs YAML frontmatter with `name` and `description` (look at
  any installed skill for the format).
