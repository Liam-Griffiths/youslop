# T3.2 Claude vision review and REVIEW.md
Phase 3 · Size M · Depends on: T3.1

## Goal
A review job sends a **targeted** set of snapshot frames to Claude (about
8 to 12 by default; everything only on request), gets back
P0/P1/P2 notes written as a stranger describing what they see, stores them as
`review/notes.json`, writes a human `REVIEW.md`, and summarises on
`Project.review`.

## Why
This is the half of the Hyperframes loop that actually catches bad video:
"describe the frame as someone who has never seen the script". Numbers
(T1.5) find structural faults; eyes find ugly ones.

## Read first
- `app/llm.py`: `complete_json(prompt, *, images=None, ...)` at ~153 and
  `_image_blocks` ~236; how `app/identify.py` calls it with images. Note the
  model/size limits it enforces.
- `app/review.py` (T3.1): manifest shape.
- `app/check.py` (T1.5): `Finding` dataclass; reuse the same severity
  vocabulary and `fix` payload shape so the UI panel (T1.6) can show both.
- `app/schema.py`: `Project` (~542); where `problems` or similar summaries
  live. Add `review: dict = field(default_factory=dict)`.
- Hyperframes `review.md` doctrine (summarised in `docs/roadmap.md` §3 and
  §4 row 3.2): never a score; weakest shot named; fix order = text, then
  timing, then detail; P0 blocks render, P1 should fix, P2 taste.

## Steps
1. Prompt builder `review.prompt_for(batch, story_slice, frame)`:
   system: "You are a stranger watching this on a phone with the sound off.
   Describe each frame in one sentence before judging it." Ask for JSON:
   `{"notes":[{"t":..,"severity":"P0|P1|P2","see":"...","problem":"...","fix":{"kind":"text|cue|picture|timing|title|look","slide_id":..,"hint":"..."}}],"weakest":{"t":..,"why":".."}}`.
   Include the FrameSpec `rules` and `rejected_looks` so Claude knows the
   house doctrine. No scores anywhere in the schema.
2. **Frame selection (owner decision 2026-10-26: targeted by default).**
   `review.select(snaps, findings, mode="targeted"|"full") -> list` in
   `app/review.py`, pure. Targeted takes, in priority order and deduped
   within 0.5 s: one frame per P0 and P1 finding from `check.run` (the
   numbers already say something is wrong there); the hook beats at 0.0,
   1.5 and 3.0 s; the last frame of the video; and the first frame of each
   chapter. Cap at 12, dropping chapter frames first, then P1s, never P0s
   or hook frames. `full` takes every snapshot. The default everywhere (API,
   CLI, UI button) is `targeted`; "Review every frame" is a separate,
   labelled action.
   Batching: one call for targeted (≤ 12 images); `full` batches 16 per call.
   If mandatory P0 and hook frames alone exceed 12, refuse targeted with
   an actionable `--full` message rather than dropping them.
   Downscale to 640 px wide before sending. Each image is captioned with its
   timecode and `why` so Claude can refer to it. Merge batch results; keep
   one `weakest` (the one Claude picks in the last batch, or the P0 with the
   smallest t).
3. `review.run(project, progress) -> dict`: snapshots (reuse if fresh; the
   manifest stores a `storyboard_hash`, not the unrelated save stamp), batches, merge, write
   `review/notes.json` (with `"mode"` and `"frames_sent"`), write
   `review/REVIEW.md` with headings exactly:
   `## What was looked at` (mode, count, times, and how many snapshots were
   not sent), `## Choices made` (from the
   storyboard: format, theme, camera ops used), `## Measured` (T1.5 findings
   count by severity), `## Looked at` (the notes grouped P0, P1, P2),
   `## Weakest shot`, `## Warnings kept` (dismissed items from a previous
   run, see T3.3). Set `Project.review = {"at": iso, "p0": n, "p1": n,
   "p2": n, "weakest_t": t, "path": "review/REVIEW.md"}` under
   `store.lock_for(pid)`.
4. API `POST /api/projects/{pid}/review {mode}` starts the job (default
   `targeted`); `GET` returns notes.json. CLI `review PID [--full] [--json]`,
   exit 1 if any P0.
5. Timeline panel (T1.6 added a Check panel): add a "Review" section listing
   notes with jump-to and the frame thumbnail; the weakest shot pinned at
   the top.
6. Test with a fake `complete_json` (monkeypatch) returning canned JSON:
   `select` keeps every P0 and hook frame and caps at 12; targeted makes
   exactly one call; full batching splits at 16, merge keeps severities, REVIEW.md has all six
   headings, `Project.review` counts match.

## Acceptance
- `cli review` sends at most 12 frames in one call (log line says how many
  and why each was picked); `cli review --full` sends all snapshots.
- `cli review` on the test project produces REVIEW.md that a reader can act
  on without opening the app, with no numeric score anywhere.
- The Timeline Review section jumps to a note's `t`.

## Don't
- No "7/10" or stars. If Claude returns a score, drop the key.
- Do not send full-resolution frames; 640 px wide.
- Do not make `full` the default anywhere, including in the skill (T3.5).
- Do not auto-apply any fix here; T3.3 does routing with the user in the loop.

## Implementer notes
*Added 2026-10-26.*

- `complete_json(prompt, system=, model=, timeout=, require=, require_hint=, images=[bytes])`
  works on all backends: CLI (sends stream-json with image blocks on
  stdin), API (`_image_blocks`), Ollama (base64 `images`). There is no size
  cap in `llm.py`; you must downscale yourself. JPEG at quality 85, 640 px
  wide keeps 16 images well under request limits. Use `MODEL_UTILITY`
  (Sonnet) unless the owner says otherwise.
- `complete_json` takes **one prompt string** and images go before it, so
  the per-image captions must be in the prompt text, in order:
  `Image 1: 00:12.40 (cue: "the first ad")` ... Tell the model to reference
  images by that timecode in `t`.
- Use `require=lambda v: isinstance(v, dict) and isinstance(v.get("notes"), list)`
  so a malformed reply is retried by the existing machinery.
- Score-stripping: after parsing, recursively drop keys matching
  `score|rating|grade|stars|/10` and log that it happened.
- `Project.review` field: add to the dataclass with
  `field(default_factory=dict)` **and** to the hand-written
  `Project.to_dict()` (it does not use `asdict`; see T1.1 notes).
- Staleness of snapshots: the manifest should store
  `storyboard_hash = sha1(json.dumps(storyboard.build(p), sort_keys=True))`
  rather than `updated_at` (which changes on unrelated saves).
- Write files outside the lock; take `store.lock_for(pid)` only for the
  final `p.review = ...; store.save(p)` (reload inside the lock first:
  `p = store.load(pid)`), because the review can take minutes and the UI
  saves meanwhile.
