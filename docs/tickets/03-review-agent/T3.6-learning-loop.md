# T3.6 Learning loop: rules, rejected looks, formats
Phase 3 · Size S · Depends on: T1.1, T3.2

## Goal
Three small actions turn feedback into persistent behaviour: "make this a
rule" appends to the frame spec's `rules`, "reject this look" appends to
`rejected_looks` and is honoured by every picker, and "save as format"
snapshots style + frame + look onto the channel for reuse at `new_project`.

## Why
The WeAreNoCode skill's biggest idea: every note becomes a rule, so the
same mistake is never made twice. It costs almost nothing given `FrameSpec`.

## Steps
1. Rules: `POST /api/projects/{pid}/frame/rules {text, scope: project|channel}`
   appends a trimmed line (max 200 chars, dedupe). `prompt_block` emits
   `rules` under a "House rules" heading, newest last. UI: a "Make this a
   rule" button on each review note and in the Ask panel, prefilled with
   the note's `problem`.
2. Rejected looks: `POST .../frame/rejected {look, scope}` where `look` is a
   token from a fixed vocabulary: camera op names, transition names, theme
   keys, cut format keys, title styles. `_pick_op`, theme choice, cut
   choice and `_join_for` all skip rejected tokens (fall through to the
   next candidate; never leave a slot empty). Review note `fix.kind=look`
   routes here (T3.3).
3. Formats: `Channel.formats: list[dict]` of
   `{name, style, frame, look: {theme, cut, intro, outro}}`.
   `POST /api/channels/{cid}/formats {name}` snapshots from a project;
   `new_project(..., format_name=)` applies it. UI: "Save as format" in the
   project's channel section; a format dropdown on the new-project form.
4. CLI: `rule add "<text>"`, `look reject <token>`, `format save <name>`,
   `format list`.
5. Tests: rule dedupe and prompt emission; a rejected camera op is never
   returned by `_pick_op` over 200 picks; `new_project` with a format copies
   style and frame.

## Acceptance
- Rejecting `punch` on a channel: the next plan on a project in that channel
  uses no `punch` op (check the storyboard).
- A saved format appears when creating a new project and applies.

## Verify
```sh
.venv/bin/pytest tests/unit/test_learning.py -q
```

## Don't
- No free-text looks; tokens only, or pickers cannot honour them.
- Do not let channel rules silently overwrite project rules; both lists are
  emitted, channel first.

## Implementer notes
*Added 2026-10-26.*

- Channel rules vs project rules: `prompt_block` currently only sees
  `project.frame`. Since `new_project` deep-copies the channel's frame
  (T1.1), channel rules added **after** a project was created would not
  reach it. Emit both at prompt time:
  `rules = channel.frame.rules + [r for r in project.frame.rules if r not in channel.frame.rules]`.
  So `prompt_block` needs an optional `channel_frame` argument; update
  `_frame_text(project)` (T1.3) to load the channel via
  `channels.load_or_none(project.channel_id)`. Same merge for
  `rejected_looks`.
- Token vocabulary, as one constant both API validation and pickers use:
  ```python
  LOOK_TOKENS = {
      "camera": set(render.CAMERA_OPS),                 # T1.4
      "join": {"cut", "fade", "dip", "wipeleft", ...},  # T1.4 JOIN_XFADE keys
      "theme": set(themes.THEME_KEYS),
      "cut": set(cuts.BY_KEY),
  }
  ```
  Store tokens namespaced (`"camera:punch"`) so `punch` the op and a
  hypothetical theme called `punch` cannot collide.
- "Never leave a slot empty": if every candidate is rejected, fall back to
  the first candidate and log a warning, rather than raising.
- `Channel.formats` must be added to the hand-written `Channel.to_dict()`
  and excluded/handled in `from_dict` (see T1.1 notes; the same trap).
- `new_project` is called from the create endpoint (grep `new_project(`
  in `main.py`); add `format_name` there and pass it through.
