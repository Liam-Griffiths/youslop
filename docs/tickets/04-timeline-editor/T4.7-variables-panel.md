# T4.7 Variables panel
Phase 4 · Size S · Depends on: T4.3, T1.1

## Goal
A Variables panel on the Timeline lists the channel's colours, copy strings
and frame-spec numbers that the current project actually uses, lets the user
edit them, and scene templates read the same values as `data-var-*` and CSS
variables.

## Why
Hyperframes' Variables panel is the thing that makes a template reusable
across episodes. Ours already has the data (theme palette, channel copy,
FrameSpec); it has no one place to see and edit it.

## Read first
- `app/themes.py`: `palette` ~140, `apply_to_style` ~159; `Style` fields
  ~172 in `schema.py` (`accent`, fonts).
- `app/schema.py`: `Channel` (name, handle, subscribe copy, slate text),
  `FrameSpec` (T1.1).
- `app/scenes.py` `context_base` (T2.3): what variables scenes already get.
- `static/scene/runtime.js` (T2.2): `data-var-text`, `data-var-src`,
  `var(--id)` handling.
- `static/js/timeline/variables.js` placeholder (T4.1).

## Steps
1. Server: `GET /api/projects/{pid}/variables` returns
   `{colors: {accent, bg, ink, ...}, copy: {channel_name, tagline, handle, subscribe}, frame: {arrive_s, exit_ratio, ...}}` each entry
   `{value, source: project|channel|theme|default}`.
   `PATCH` with `{scope: project|channel, key, value}` writes to the right
   object under the lock and returns the recomputed set. Copy maps to
   `Channel.name`, `Channel.tagline`, `Channel.outro.handle`, and
   `Channel.outro.cta` (subscribe copy), or standalone project title/subtitle
   and outro fields. There is no `slate_kicker` schema field. `bg` and `ink`
   are theme-only, read-only values; only accent/accent2 are style fields.
2. `scenes.context_base` is built from the same function, so the panel and
   the templates can never disagree. Each colour is emitted as `--<key>` on
   the composition root; each copy string is available as `{{ copy.x }}`
   and as `data-var-text="copy.x"`.
3. `static/js/timeline/variables.js`: three groups with a search box;
   colours show a swatch and a hex input; copy shows a text input; frame
   numbers show mono inputs with units. A "source" tag per row; editing a
   theme-sourced colour writes to the project style (override) and the tag
   changes to `project`; a Reset button restores the current channel/theme value.
   Styles and FrameSpecs are complete snapshots copied at project creation,
   so sources are inferred by comparison, not stored override metadata. Channel
   scope changes defaults for future projects; existing snapshots stay intact.
4. Changing a variable invalidates scene clips for the project
   (`scenes.ensure_clip` key includes a hash of the variables; confirm T2.3
   did this; if not, add it) and refreshes affected proxies lazily.
5. Tests: `variables()` sources are correct for a project with and without
   overrides; a `PATCH` of `accent` is visible in `scenes.context_base`.

## Implementer notes
*Added 2026-10-26.*

- After T2.2's notes, scene templates read variables two ways: our own
  `data-var-text`/CSS custom properties, and catalog components'
  `window.__hyperframes.getVariables()` fed from `data-variable-values`.
  The panel only needs to feed `scenes.context_base`; templates pass
  values on to mounted components explicitly.
- Theme tokens catalog components expect: `--fg --bg --brand --accent
  --accent-2 --font-display`. Emit those names on the composition root
  from `themes.palette(style)` (map: `ground → --bg`, `ink → --fg`,
  `accent → --accent` and `--brand`, `accent2 → --accent-2`) so catalog
  blocks pick up the channel colours with no per-block wiring.
- "Source" resolution order: project style override → channel style →
  theme → default. `themes.palette(style)` already merges theme and style;
  read its code to see which keys it fills, then label anything equal to
  the theme value as `theme`.
- The music level is `style.music_db` (T1.7 removed `duck_db`).
