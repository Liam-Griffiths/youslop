# T12.8 Block library: browse, preview and use blocks app-wide
Phase 12 · Size L · Depends on: T12.1, T12.3, T9.3
*Written 2026-11-08 (Claude Opus 5.5) from the owner's brief; anchors checked against `dev` at that date.*

## Goal
A new top-level **Blocks** screen (`#/blocks`, in the app nav between Library and Channels) shows every block the app knows (built in, packs, mine) in one rich, searchable grid with locally made previews, a detail panel where you try a block with your own text in either aspect, and one-click actions to use it in a project, add it to a channel or duplicate it as your own. The same browser component is what the Visuals stage (T12.5) and the channel page open.

## Why
Owner, 2026-11-08: blocks should be app-wide, not tied to any one project, and the library should be rich, accessible and intuitive. The registry is already app-wide (`blocks.discover()`), but the only UI is a `<select>` in Library and the only previews are a contact sheet in `docs/`. People cannot use what they cannot see.

## Principle: one library, customisation is data
- Block **code** lives in one place per source: built in (`static/blocks/`), packs, or mine (`blocks.USER_DIR`). Nothing is copied into a project or a channel.
- Channels and projects customise blocks with **presets** (saved variable values and pins, T12.9), not copies of the code.
- "Duplicate as mine" is the only way to change a block's code; it forks into `USER_DIR` with origin metadata and becomes app-wide like any other block.

## Steps
**Implementation batches (2026-11-08):** Per README's ~600-line diff rule,
this change implements steps 1–3, basic search/filters and read-only details.
The remaining steps and acceptance checks continue in
[T12.8b](T12.8b-block-library-actions.md). Keep Library's existing controls
until their replacements land. The browser script lives in
`static/js/tabs/blocks_browser.js` to satisfy the existing script-order contract.

1. **Route and nav.** Add `Blocks` to the app nav in `paintAppNav` (`static/js/shell.js`) between Library and Channels, routed at `#/blocks` (and `#/blocks/<ref>` to open one block's details). Owner, 2026-11-08: Library is about images and footage; blocks are different enough to be their own screen. Library stays as it is apart from step 10. The screen shows a left filter column, a poster grid and a right detail panel (the shell inspector slot).
2. **Block metadata for browsing.** `GET /api/blocks` returns, per block: ref, name, one-line description, kind/category, tags, aspects supported, duration range, source (`built-in` | pack name | `mine`), licence, origin (forked-from, described-by), check status, and which channels pin it. Add missing `description`/`tags`/`category` to the 31 core blocks' `block.json` where absent. Keep the schema backward compatible (optional fields).
3. **Posters.** One still per block per aspect, from authored defaults, drawn locally with the existing builder path and cached at `data_root/.cache/blocks/posters/<ref>/<signature>-<aspect>.png`. The signature covers the block's files and defaults, so edits invalidate it. Missing posters are made by ONE background job (`jobs.start`) that reuses a single Chromium session for the batch; the grid shows a neutral placeholder with the block name until each arrives. Never generate on every page load. Serve them via `GET /api/blocks/{ref}/poster?aspect=`.
4. **Motion preview.** On hover after 400 ms, on keyboard focus plus Space, or with the detail panel's Play button, play a short quarter-size loop of the block. It is made on first request with `blocks.render` at quarter size and the default length (capped at 6 s), cached beside the poster, and only one is generated at a time; later requests queue or cancel the stale one. Respect `prefers-reduced-motion`: show the poster and a Play button, with no autoplay.
5. **Find.** Search (name, description, tags, variable names), filter chips for category, aspect (16:9 / 9:16), source (built in / packs / mine / pinned to channel X) and "works with data", plus sort (recommended, recently used, A–Z). Favourites (star) and "Recently used" are per user, stored app-wide in the data root (not localStorage). Empty states say what to do next ("No blocks match. Clear filters" / "Describe a block" when the search finds nothing).
6. **Detail panel: try it.** A big poster, an aspect toggle, Play, licence, source, origin and check status. Below that, the variable form is generated from `block.json` (text with live max-length counters, colour tokens, image pickers using the shared picker, `table` with "Paste CSV" via `validate_vars`). Editing a value refreshes the poster at quarter size (debounced about 600 ms, one in flight, stale results dropped). "Reset to defaults". The trial values are scratch: nothing is saved unless the user picks an action.
7. **Actions** (the panel footer, all keyboard reachable):
   - **Use in a project…**: choose the project and paragraph or slide (the current project first if one is open); apply the trial values as `cues.blocks` through the existing slide PATCH API and `app/edits.py:patch_slide_fields`. Visuals currently links to the browser and has no direct block-apply action.
   - **Add to channel…**: pin it to a channel (today's `POST /api/channels/{cid}/blocks`); T12.9 adds saving the trial values as the channel preset.
   - **Duplicate as mine**: fork into `USER_DIR/<slug>` with `origin.forked_from`, re-run `block check`, then open it. Never edit built-in or pack blocks in place.
   - **Describe a block**: T12.6's form moves here, as a card at the top of the grid and a button in empty states.
8. **Accessibility.** The grid is a list of buttons with visible names (not image-only); arrow keys move between cards and Enter opens the details; focus rings are visible; posters have alt text "<name>, <aspect> preview"; the motion preview is never the only way to understand a block (the description and variables list are always shown); contrast meets the tokens; it works at 1100 px and on a phone width without horizontal scroll.
9. **Reusable component.** Build the grid, filters and detail panel as one component (`static/js/blocks_browser.js`, a plain script tag) with modes `library` (all actions), `pick` (T12.5: "Use here" replaces "Use in a project…") and `channel` (T12.9: pin and preset). Keep it out of `media.js`.
10. **Remove** the old block `<select>`, "Add to channel" row and T12.6's describe form from the Library page; replace them with one line linking to Blocks.

## Acceptance
- Every built-in, pack and user block appears in `#/blocks` with a local poster in both aspects after the poster job finishes; no network requests for previews.
- Typing "number" or "map" finds the right core blocks; filtering to 9:16 shows only blocks that support portrait.
- Hovering or focusing a card plays a quarter-size loop within about 2 s on a warm cache, and only one loop renders at a time.
- Editing a headline in the detail panel updates the poster, and the counter shows the remaining characters; an over-length value shows the check error inline.
- "Use in a project…" puts the block on the chosen slide with those values; "Duplicate as mine" creates `user/<slug>` that passes check and shows under Mine.
- Keyboard only: find a block, preview it, change a value and use it in a project, with no mouse.
- The UI snapshot harness covers `#/blocks` and `#/blocks/<ref>` (grid, detail panel open, empty search) with 0 console errors.

## Don't
- No per-project or per-channel copies of block code (T12.9 does presets).
- No upstream or third-party preview images; third-party blocks stay in their separate, labelled section only when T2.7c's setting is on.
- No full renders, no per-frame CDP, no motion previews generated in bulk.

## Implementer notes
- `blocks.render(..., project=None)` already caches under `data_root/.cache/blocks`; reuse it for motion previews rather than a new path.
- `discover()` rescans on every call; cache the browse metadata per request batch, keyed by the folders' mtimes, so the grid doesn't revalidate 39 folders per poster request.
