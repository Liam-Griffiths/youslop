# T12.6 Make a block from a description
Phase 12 · Size M · Depends on: T12.2
*Written 2026-10-31 (Claude Opus 5.5) from the owner's brief; anchors checked against `dev` at that date.*

## Goal
A user (or the channel) can describe a block ("a receipt that prints line by line with a total at the end"); Claude writes one block once, it must pass `block check`, and it is saved as the user's own block for reuse with variables, so later uses cost no tokens.

## Why
This is where we beat a code-per-scene workflow: the model writes a reusable, checked block once instead of new code for every scene.

## Read first
- T12.2 checks; `llm.complete_json`; the scaffold; T3.6 learning loop (saved formats).

## Steps
1. Prompt with the scaffold, builder contract, two built-in examples, tokens,
   safe areas and check rules; ask for `block.html` + `block.json` only.
   Accept the restricted Jinja/HTML vocabulary in Implementer notes and render
   user blocks through a sandbox with the shared app-owned `data-fit` helper.
2. Check an isolated temporary candidate with `block_authoring.check` and
   builder stats at 10 seconds; feed quoted failures back at most twice.
   Never publish a failed candidate. Tests mock the browser checker.
3. Save to `blocks.USER_DIR/<slug>` with collision suffixes and origin metadata;
   offer "add to channel" using a default-empty `Channel.blocks` list.
4. Library has no block list yet: add the list and "Describe a block" form
   there, using `jobs.start`. Preserve provider-reported usage (the LLM wrapper
   currently discards it), and show the one-off token usage or its unavailability.

## Acceptance
- Mocked runs produce a block that passes check; a failing block after two retries is not saved.

## Verify
```sh
.venv/bin/pytest tests/unit/test_blocks.py -q
```

## Don't
- Never call a real model in tests; never save a block that fails check.

## Implementer notes
*Added 2026-11-01 (Claude Opus 5.5). The owner's scope for the scene builder:
"templates, blocks, and then custom scene creation when appropriate". This ticket
is that custom creation, so its output must render as fast as the built-ins.*

- **Builder contract in the prompt.** Every generated block renders through
  `scene_builder` (T2.8/T2.10): one `data-layer` per independently timed element,
  motion only from `static/scene/motion.json` presets via `data-motion`, pictures
  as `data-media`, `budget: 0` (no capture windows). Text that arrives word by
  word is one layer with a wipe, never a layer per word. Include two or three
  T12.3 blocks as examples (e.g. `lower_third_rule`, `number_slam`, `step_list`)
  plus the scaffold in `block_authoring.TEMPLATE`, the token list, safe areas and
  the type floor (44 px at 1080 for labels/values).
- **Check = the T12.2 check plus builder stats.** Reject (and feed back) a block
  whose `block check` fails, whose stats show capture-window frames, more than
  12 layers, or more than one pass for a 10 s block. Feedback quotes the errors.
- **Untrusted output.** The model writes Jinja and HTML that the app will run.
  Accept only `{% extends "_base.html" %}` (or a built-in block base) plus
  `{% block %}`/`{{ vars.x }}`/simple `{% if %}`/`{% for %}`; reject `import`,
  `include`, `macro` imports from other paths, attribute access beyond `vars`,
  `width`, `height`, `duration` and `data`. Render user blocks with a
  `jinja2.sandbox.SandboxedEnvironment`. No `<script>`, no `<iframe>`, no
  `on*=` handlers, no `url(`/`src=` outside `/fonts/`, the block's own assets or
  `data:` images; no `http(s):`. If fitting text needs script, provide one shared,
  app-owned include for `data-fit` and let blocks use the attribute only. Add
  adversarial tests.
- **Storage and ids.** Save to `blocks.USER_DIR/<slug>` only after the check
  passes; never overwrite an existing id (append `-2`, `-3`). Record the prompt
  description, model, token usage and creation date in `block.json`
  (`origin`), and show the token cost in the UI result.
- **Where it lives in the UI.** A "Describe a block" form next to wherever block
  lists are shown today (search `blocks` in `static/js/`); run it as a job
  (`jobs.start`), LLM call outside any project lock. "Add to channel" stores the
  block id on the channel (find how channel block picks are stored, or add a
  small list on `Channel` with a default of empty).
- Tests mock `llm.complete_json`: one passing run, one that fails twice and is
  not saved, one that passes on the second attempt, and the sandbox rejections.
  Chromium is unavailable: mock `block_authoring.check`; the reviewer runs one
  real creation with the owner's Claude setup only if the owner asks.
