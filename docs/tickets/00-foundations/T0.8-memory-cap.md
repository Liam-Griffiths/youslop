# T0.8 Re-measure the render memory cap
Phase 0 · Size S · Depends on: —

## Goal
The segment pool size in `render.render()` is derived from a measured number
with the measurement recorded next to it.

## Why
`NEXT_STEPS.md` §1: the `free_mb // 5000` divisor dates from when an essay
segment re-decoded a 1080p PNG per frame. That is fixed (`HOLD_STILL`), so a
16 GB machine is probably rendering three segments at once when it could run
six. Cheapest total-render-time win available.

## Read first
- `app/render.py`: `render()`, the line `workers = max(1, min(workers, int(free_mb // 5000)))`, `HOLD_STILL`.
- `NEXT_STEPS.md` §1.

## Steps
1. Add `scripts/measure_segment_rss.py`: loads a project id from argv,
   picks one essay segment and one documentary segment, runs
   `_render_segment` for each under `/usr/bin/time -v` (Linux/macOS) and
   parses "Maximum resident set size". Prints both in MB. This is **opt-in
   and heavy**; say so in the docstring and print a warning before starting.
2. Run it once on this machine on a real project. Record the two numbers in
   the ticket log.
3. In `render.py`, replace `5000` with a module constant
   `SEGMENT_RSS_MB = <measured peak, rounded up to the nearest 500>` and a
   comment with the date, machine and numbers.

## Acceptance
- The constant exists with a comment citing the measurement.
- `render()` logs the worker count it chose (it may already; check).

## Verify
```sh
.venv/bin/python scripts/measure_segment_rss.py <pid>    # heavy: two single-segment renders
grep -n "SEGMENT_RSS_MB" app/render.py
```

## Don't
- Do not render a whole project.

## Implementer notes
*Added 2026-10-26. Say before running anything heavy; the owner feels it.*

- There are **two** divisors in `render.py`: `free_mb // 5000` in `render()`
  (~line 1218, ffmpeg segment threads) and `free_mb // 800` in
  `_draw_segments` (~195, drawn-cut processes). This ticket is the first
  one only. The comment above it says the 4-5 GB figure is the *essay*
  caption graph depth, so the honest outcome may be a per-format number:
  ```python
  # Peak RSS of one segment encode, measured <date> on <machine>: essay X MB, kenburns Y MB.
  SEGMENT_RSS_MB = {"essay": X, "default": Y}
  per = SEGMENT_RSS_MB.get(project.style.format, SEGMENT_RSS_MB["default"])
  workers = max(1, min(workers, int(free_mb // per)))
  progress(f"{workers} segments at a time ({free_mb} MB free, {per} MB each)")
  ```
- Measure with `resource`, not `/usr/bin/time`: the RSS that matters is the
  ffmpeg child, and `getrusage(RUSAGE_CHILDREN).ru_maxrss` gives the largest
  waited-for child (kB on Linux, bytes on macOS). Run each segment in a fresh
  `subprocess` of the script itself so the two measurements do not share a
  maximum:
  ```python
  # scripts/measure_segment_rss.py <pid> <segment-index> <format>
  # parent: for fmt in ("essay", "kenburns"): subprocess.run([sys.executable, __file__, pid, idx, fmt, "--child"])
  # child: p = store.load(pid); p.style.format = fmt   # in memory only, never saved
  #        render._render_segment(p, groups[idx], seg_len, idx, out_in_tmpdir)
  #        print(resource.getrusage(resource.RUSAGE_CHILDREN).ru_maxrss / 1024, "MB")
  ```
  Use `_layout(p)["groups"]` and `_segment_timing` to get the group and
  `seg_len` exactly as `render()` does. Write output to a temp dir, not the
  project's `segments/`.
- The only project with real content is `pf0bf417b` (essay, 12 groups) in
  `~/.local/share/youslop`. Run with
  `YOUSLOP_DATA=~/.local/share/youslop`. Overriding `format` in memory gives
  you the documentary measurement from the same pictures. Never `store.save`.
- Pick the essay group with the **most paragraphs** (deepest caption chain)
  for the worst case.
- `if __name__ == "__main__":` guard is required (process pools re-import).
