# T5.3e Drawn cut to scene: Casefile
Phase 5 · Size L · Depends on: T2.4, T0.6, T5.3d

## Goal
The **Casefile** cut renders through the scene engine from the same plan the cut's
`PLAN` prompt already produces: `kit.place` keeps the timing, cues become
builder screens, and `cuts.still()` encodes one builder frame.

## Why
Last because its corkboard texture, tape and pins are the most Pillow-friendly; CSS textures plus SVG tape must match the current feel before it ships.

## Read first

  block/layout helpers and the per-frame draw function (the last big

- `app/cuts/kit.py`: `place` ~438 (timing), `fit` ~102, the eases

## Steps
1. Write `docs/tickets/05-migrations/notes-casefile.md` first: a table of every
   visual element the Pillow drawer produces (name, when it appears, how it
   moves, ease) by reading the draw function. This is the spec for the
   template; do not start the template without it.
2. Add `app/cuts/casefile_scene.py` and `static/scene/cuts/casefile.html` +
   `casefile.css` using the Builder conventions below: cue screens, settled
   history grounds, one layer per moving text row, native ffmpeg photo posters,
   shared camera/motion presets. Reuse `_boards`/`_slots` and `kit.place`;
   Casefile has no `_palette`, so resolve its three `_ground` colours in context.
3. Register `casefile` in `scenes.handles_cut`; use the existing generic drawer
   dispatch inside `cuts.render_segment` through `scene_builder.render`.
   Preserve frame ranges, rounded-up counts, chapter tail and one-frame stills.
4. Document the three-time comparison recipe under `compare/casefile/` and
   deliberate visual differences in the element notes. Chromium is unavailable
   during implementation: mock probes/captures, leave real comparison images
   and frame/speed judgement to the reviewer.
5. Opt-in SSIM test against the first reviewer-accepted scene golden
   (`YS_VISUAL=1`); skip explicitly until that real capture exists.
6. Keep the Pillow drawer behind `style.cut_engine="pillow"`.

## Implementer notes
*Added 2026-10-26. These notes are shared by T5.3a-e; the first bullet is
a decision that T5.3a must make once for all five.*

- **Decide where the scene branch lives (T5.3a only, then follow it).**
  T2.4 put a generic `scenes.handles(style.format)` check at the top of
  `render._render_segment`, keyed on `static/scene/<fmt>/segment.html`.
  For the drawn cuts that would **bypass `cuts.render_segment`**, which
  owns the beat layout (`lead_in` per paragraph, the final paragraph
  taking the remainder), the chapter screen at `seg_len - hold`, and the
  frame-count rule (`frame_count()` rounds up so xfade never runs past
  the end). Do the branch **inside `cuts.render_segment`** instead, after
  `beats` are built, and name templates `static/scene/cuts/<key>.html`
  with `scenes.handles_cut(key)` (and `style.cut_engine != "pillow"`).
  Keep T2.4's generic branch for non-cut formats only (skip it when
  `cuts.is_cut(fmt)`). Ticket step 3's `handles("cut:<key>")` is the
  same idea with a different spelling; pick one and record it here.
- **Chunking.** `render._draw_segments` cuts long drawn segments into
  ~`CHUNK_SECONDS` (20 s) pieces and renders them in a **spawn process
  pool**, passing `frames=(a, b)` to `cuts.render_segment`, then
  concatenates. A scene render must honour `frames=(a, b)` (seek from
  `a/fps`, capture `b - a` frames) **or** `_draw_segments` must not
  chunk scene-engine segments. Honouring `frames` is easy with seek-based
  capture and keeps the parallelism; but each piece launches its own
  Chromium, so cap concurrency at 3 for scene cuts (Chromium is ~300 MB
  and multi-threaded itself). Measure, then set the cap.
- **Context the template needs**, all already computed in
  `render_segment`: for each beat, `slide.id`, its `length`, `lead`,
  the cues from `cues_for(module, slide)` with times from `kit.place`
  (`beat_for` does this; after T0.7 use `timed_cues`), the picture URL
  via `source_for(ctx, slide)` served under `/scene/<token>/project/`,
  `ctx.accent`, `ctx.accent2`, `ctx.look` (the cut's LOOKS key) and
  the module's palette output (Casefile instead resolves its `_ground` look
  colours in the context module; do not re-derive colours in CSS).
- **Write the element table from `frame()`** (`app/cuts/casefile.py`,
  `def frame(beat, ctx, t)`). It is a pure function of `t`: every
  appearance is an `if t >= ...` and every motion is `kit.ease_*(u)` of
  some `u = (t - start) / dur`. Ease mapping (checked against `kit.py`
  2026-10-26): `kit.ease_out` = `1-(1-t)^3` → `cubic-out`;
  `kit.ease_in_out` = cubic in-out → `cubic-in-out`; `kit.ease_back(t,
  s=1.9)` → `back-out-1.9` (pass the same `s` when a call site overrides
  it); `kit.lerp` with no ease → `linear`. Faces: `kit.FACES` maps
  `display` → `ArchivoBlack-Regular.ttf`, `sans_bold` →
  `Inter-Bold.ttf`, etc.; `@font-face` those exact files.
- **Looks.** `LOOKS` / `LOOK_COLORS` switch ground and ink; express
  each look as a CSS class on the root (`.look-paper`) setting the
  custom properties, so one template covers all looks.
- **Comparing.** Pillow vs scene SSIM is meaningless (different
  rasterisers). The golden for the opt-in visual test is the **scene's
  own** first accepted capture. The real check is the human side-by-side
  under `compare/casefile/` plus unchanged cue times from `timeline()`.


### Builder conventions from T5.3a (2026-11-01; supersede the GSAP wording above)
Read T5.3a's Round 3, Round 4 and review logs, `app/cuts/loudmouth_scene.py`,
`static/scene/cuts/loudmouth.html` and `docs/scene-builder.md` first.
- Render only through `scene_builder.render` from `cuts.render_segment`'s scene
  branch (`uses_scene`); add a `<key>_scene.py` context module like Loudmouth's and
  a template `static/scene/cuts/<key>.html` (+ `.css`). Generalise the branch to
  dispatch by cut key rather than special-casing Loudmouth.
- Screens at cue boundaries; settled content belongs to later screens' grounds.
  Moving text is one layer per row (stepped reveal for word-by-word), never per word
  or letter. Pictures and video come straight from the source in ffmpeg.
- Motions the shared table lacks go into `static/scene/motion.json` and the
  compiler (shared, unit-tested), not a private compositor. Capture windows
  (`data-capture="frames"`) only for an effect ffmpeg truly cannot express, within
  budget, and say why in the Log.
- Avoid position-dependent CSS selectors (`:nth-*`, `:first-*`, `+`, `~`) in the
  template: they force the slow full-style probe. Use classes.
- Keep `cut_engine="pillow"` and the Pillow drawer. Mock Chromium in tests.
- Reviewer target: one picture via `preview_segment` at 480x270, cold no slower
  than 2x this cut's Pillow time; frames recognisably the same format.

### 2026-11-01 — review of round 1 (Claude Opus 5.5)

One picture (`s361e0037`, 88 s), 480x270: Pillow 3.9 s; scene as delivered 11.8 s
cold, 9.05 s warm. Every pass took 2.5–5 s: native still media were looped *before*
their scale/crop/blur/dim, so those ran on every frame, and a constant-alpha `geq`
ran on every frame too. Builder fix (shared): filter a still once, then loop; skip
the alpha `geq` when the mask is constant and window it to the arrival when it only
animates opacity. Now **cold 6.35 s, warm 3.56 s** (target 7.8 s); frames identical
before/after the fix. 966 unit tests pass.

Look (`compare/casefile/pillow-top-scene-bottom-r1.png`) is not yet the same format:
1. Ground: Pillow's warm brown cork (colourised noise with dark specks; `wall` and
   `felt` looks differ) reads as a dark grid pattern in the scene.
2. Lamp: Pillow lays a warm vignette over the *frame* (screen space, after the
   camera; `_light`). The scene has none, so the board looks flat and dark-edged.
3. Photos: Pillow shows them desaturated/greyscale (`ImageOps.grayscale` path);
   the scene shows full colour.
4. Index cards: text overflows the card's right edge ("celebrity goss…") and does
   not sit on the ruled lines.
