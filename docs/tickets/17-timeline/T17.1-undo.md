# T17.1 Undo and redo for project edits
Phase 17 · Size M · Depends on: —

## Goal
Ctrl+Z and Ctrl+Shift+Z (and buttons) undo and redo project edits made in the
studio, the timeline above all.

## Why
Every Phase 17 ticket adds bigger edits: inserting, reordering, rippling.
People try things on a timeline. Without undo, a wrong drag is a manual repair.

## Read first
- `app/store.py`: `save`, `load`, `lock_for`; `app/edits.py`; `patch_slide` in
  `app/main.py`; `static/js/timeline/edit.js` `tlSaveTiming`.
- `docs/tickets/NOTES.md` and the recorded-audio rules in `docs/tickets/README.md`.

## Steps
1. A per-project history of project-file snapshots, kept beside the project
   (e.g. `history/` with a small index), written by `store.save` when the save
   comes from a user edit. Coalesce saves within ~1 s from one gesture.
   Cap at 100 entries or ~50 MB, dropping the oldest first.
2. `POST /api/projects/{pid}/undo` and `/redo` restore a snapshot under the
   project lock and return the project. A new edit after an undo clears the
   redo branch.
3. **Audio rule:** undo restores references only. It never deletes, moves or
   overwrites a take or any media file. A take recorded after the restored
   snapshot stays in slide history (retired with reason `undo`), so redo or
   the earlier-takes UI can bring it back. If its paragraph or sponsor is absent,
   retain it in `Project.retired_takes` with its original owner id.
4. Background jobs (render, research, transcripts) must not be undone. Skip
   snapshots for job writes, and refuse undo while a job is writing that
   project (409 with a clear message). Carry completed job changes into restored
   snapshots so later undo cannot restore stale job results.
5. UI: Undo and Redo buttons in the project shell (Edit stage at least), the
   keyboard shortcuts, and a toast naming what was undone ("Undid: move
   title"). Edit sources pass a short label with the save.
6. CLI writes are already guarded by the server marker; leave CLI out of history.

## Acceptance
- Undo and redo through ten mixed timeline edits returns byte-identical
  project files, except for history added to retain newer recordings.
- A take recorded, then undone past, is still in history and still on disk.
- Jobs are unaffected; undo during a writing job is refused.

## Verify
```sh
CORKBORED_DATA="$(mktemp -d)" .venv/bin/pytest tests/unit -q
```
Reviewer: snapshot harness and a click-through in the Edit stage.

## Don't
- Don't snapshot on every autosave keystroke; coalesce.
- Never delete or overwrite recorded audio.

## Implementer notes

- `store.save` serves HTTP edits, jobs and the CLI. Mark studio request saves
  with a context variable; worker threads and CLI saves remain outside history.
  Rebase job changes at restore so a later undo cannot revert job results.
- Snapshot restoration is byte-identical except when retaining newer recordings:
  audio safety takes precedence. Keep displaced takes in the matching slide or
  sponsor history with reason `undo`; if its owner is absent, keep it in
  `Project.retired_takes` with the original owner id until it can be restored.
- The UI snapshot harness and Edit click-through are reviewer-run browser checks.

### Found in review (2026-11-11, Claude Opus 5.5)
Correctness and the audio rule look right. **The cost does not.** I measured with the Tube Mail example (`project.json` is 529 KB): 110 title edits as user saves, then one job-style save.

| | Measured | Target |
|---|---|---|
| User save, history full | 609 ms average (first 75 ms) | under 60 ms |
| Job save (`p.log.append`) | 2,172 ms (rebases and re-encodes all 100 snapshots) | no history work beyond one small read |
| Undo | 395 ms | under 150 ms |
| `history/index.json` | 52.2 MB (all snapshots in one JSON, rewritten on every save) | a few MB |

Every save runs under the project lock, so this stalls the UI and every job that writes progress.

Redesign the storage, keeping the behaviour and tests:
1. **One file per snapshot.**
   - Store `history/<seq>.json.gz` (gzip level 1) plus a small `history/index.json` holding only `{seq, label, gesture, time, bytes}` entries and the cursor.
   - A user save writes one new gz file and the small index. Coalescing overwrites the cursor's gz file.
   - Trimming deletes the oldest gz files (history snapshot files only; never media or takes).
   - Cap at 100 entries or 50 MB *compressed*.
2. **Job writes do no history work.**
   - Drop the rebase-every-state loop.
   - User edits are the only thing that makes snapshots, so at any moment the difference between the cursor's snapshot and `project.json` is exactly what jobs wrote since. At `restore`, rebase the destination snapshot with `rebase(target, cursor_snapshot, current_file)`, then `retain_recordings` as now.
   - A job save may still clear the cursor's `gesture` (cheap: index only). Skip even that if it would rewrite more than the small index.
   - Keep restored project files separate from saved baselines so job deltas
     survive successive undo/redo. If jobs ran before a subsequent user edit,
     store that edit's pre-edit baseline inside its gz file as well; restore
     uses this baseline when crossing that edit. Otherwise earlier job results
     disappear when undo crosses a newer user snapshot that includes them.
3. **Migration.** If an old single-file `history/index.json` with `payload` fields exists from this branch, convert it or discard it on first read. It never shipped, so discarding is fine.
4. **Tests.**
   - Keep the existing ones.
   - Add one asserting that a job save does not touch any `history/*.json.gz` (mtime unchanged).
   - Add a slow-gated (`YS_SLOW=1`) timing check with a 500 KB project and 100 states: user save under 60 ms, undo under 150 ms.
   - Record my bench numbers and the new ones in the Log.
