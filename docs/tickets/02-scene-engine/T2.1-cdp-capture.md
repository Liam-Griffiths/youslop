# T2.1 CDP capture mode in the stage runner
Phase 2 · Size L · Depends on: T0.5

## Goal
`app/stage.py` can render an HTML page to an mp4 by seeking it frame by frame
and screenshotting it through the Chrome DevTools Protocol (CDP), using only
the Python standard library and the system Chromium. The existing 3D "push"
mode is untouched.

## Why
This is the Hyperframes rendering model (seek a paused timeline, capture,
encode) with no Node and no Playwright. The 3D stage already launches
Chromium headless and pipes frames into ffmpeg; a DOM page cannot read its
own pixels, so the capture has to come from outside, which is what CDP is for.

## Read first
- `app/stage.py` top to bottom. In particular:
  - `browser()` finds the Chromium executable.
  - `_Run`, `_handler()` (the private HTTP server: `translate_path` serves
    `/static/…` and `/models/…`, `do_GET` serves `/job.json`, `do_POST`
    receives `/frame/<clip>` and writes bytes to an ffmpeg stdin).
  - `_begin()` starts an ffmpeg `rawvideo rgba` encoder with `-vf vflip`.
  - `_end()` checks `got == frames` and renames the `.part.mp4`.
  - `_run()` builds `cmd = [exe, "--headless=new", …, url]`, starts
    `subprocess.Popen(cmd, …)`, waits on `run.done`, kills on silence.
- `static/stage/run.js` lines 150 to 170: how the page announces `begin`,
  posts frames and `end`.
- CDP reference (read these pages, they are short): `Target.getTargets`,
  `Target.attachToTarget` (use `flatten: true`), `Page.navigate`,
  `Page.loadEventFired`, `Emulation.setDeviceMetricsOverride`,
  `Runtime.evaluate` (`awaitPromise`, `returnByValue`),
  `Page.captureScreenshot` (`format: "png"`, `fromSurface: true`).

## How the pipe works (so you do not have to discover it)
Chromium started with `--remote-debugging-pipe` reads CDP messages on **file
descriptor 3** and writes replies and events on **file descriptor 4**. Each
message is a JSON object followed by a single `\0` byte. There is no
websocket and no handshake. In Python:

```python
r_in, w_in = os.pipe()     # we write to w_in; Chromium reads fd 3 (= r_in)
r_out, w_out = os.pipe()   # Chromium writes fd 4 (= w_out); we read r_out

def _wire():               # runs in the child, before exec
    # Duplicate both ends ABOVE 4 first. A plain dup2(r_in, 3); dup2(w_out, 4)
    # silently breaks whenever w_out happens to be fd 3 (or a temp fd collides):
    # both 3 and 4 end up on the read pipe and Chromium logs "Could not write
    # into pipe". Found and fixed by test on 2026-10-26.
    a = fcntl.fcntl(r_in, fcntl.F_DUPFD, 5)
    b = fcntl.fcntl(w_out, fcntl.F_DUPFD, 5)
    os.dup2(a, 3); os.dup2(b, 4)

proc = subprocess.Popen(cmd + ["--remote-debugging-pipe"],
                        pass_fds=(3, 4), preexec_fn=_wire)
os.close(r_in); os.close(w_out)
```
*(Corrected 2026-10-26. The original snippet here had the fd-collision bug.
A tested, working prototype is in `reference/cdp_proto.py`.)*
`preexec_fn` is POSIX-only; that is acceptable (see **Don't**). Send with
`os.write(w_in, json.dumps(msg).encode() + b"\0")`. Read by accumulating
bytes from `r_out` and splitting on `\0`. Every request has an integer `id`;
the reply carries the same `id`. Events have a `method` and no `id`. After
`Target.attachToTarget`, include `"sessionId"` in every request aimed at the
page.

## Steps
1. **Add `class _Cdp`** in `stage.py`:
   - `__init__(self, w_in, r_out)`; `send(method, params=None, session=None) -> dict`
     blocks until the reply with the same id arrives, raising `StageError`
     if the reply has `"error"`; a background thread reads `r_out` and routes
     replies to per-id queues and events to a list (keep the last 200).
   - `wait_event(method, timeout)`.
2. **Add `_run_cdp(job, progress, *, out_dir, size, fps, frames, seek_js, deterministic=True) -> _Run`**
   beside `_run()`. It reuses the HTTP server and the `cmd` flags from
   `_run()` (factor the flag list into `_chromium_flags(prof, size)` and use
   it in both). Differences:
   - Append `--remote-debugging-pipe`, `--force-color-profile=srgb`,
     `--hide-scrollbars`, `--disable-gpu-vsync`, `--run-all-compositor-stages-before-draw`.
     Do **not** pass the URL on the command line; navigate via CDP so you can
     wait for load.
   - After launch: `Target.getTargets` → first `type == "page"` target →
     `Target.attachToTarget {targetId, flatten: true}` → `sessionId`.
     Then `Page.enable`, `Runtime.enable`,
     `Emulation.setDeviceMetricsOverride {width: W, height: H, deviceScaleFactor: scale, mobile: false}`
     where `scale = size[0] / W` so a 480-wide proxy is a scale of 0.25 of
     a 1920 composition. Then `Page.navigate {url}` and wait for
     `Page.loadEventFired`, then `Runtime.evaluate {expression: "window.__ready", awaitPromise: true}`
     (the scene runtime, T2.2, exposes a promise that resolves after fonts
     load).
   - Start the encoder: new `_begin_png(run, clip, W, H, fps, frames)` like
     `_begin()` but with input `-f image2pipe -c:v png -i -` and **no**
     `vflip`.
   - For `i in range(frames)`: `t = i / fps`;
     `Runtime.evaluate {expression: f"window.__seek({t})", awaitPromise: true}`;
     `Page.captureScreenshot {format: "png", fromSurface: true}`;
     `base64.b64decode(result["data"])` → write to the encoder stdin; count
     it in `clip["got"]`; call `progress` every 30 frames.
   - `_end(run, clip)` as today. Shut down exactly like `_run()` does
     (`terminate`, `wait`, `kill`, server shutdown, kill unfinished encoders).
3. **Public API.** `render_scene(items: list[dict], out_dir: Path, progress) -> dict[str, Path]`
   where each item is `{"clip": str, "url_path": str, "W", "H", "fps", "frames", "size": (w, h)}`.
   One Chromium per call, items rendered sequentially in the same page by
   navigating between them (cheaper than relaunching). Also
   `capture_one(url_path, W, H, t, size) -> bytes` returning one PNG, for
   thumbnails and review snapshots. For project scenes, items may include
   `scene_root` (one shared directory per call); use
   `/scene/{token}/relative.html` in `url_path`, with the runner substituting
   its private token. `capture_one` also accepts an absolute HTML file path
   and serves its containing directory through that tokenized route.
4. **Serving scene files.** `translate_path` must serve `/scene/<token>/…`
   from a directory the job names (`run.job["scene_root"]`), read-only. A
   token per run so a stale page cannot read another project's files.
5. **Determinism.** Before the first seek, `Runtime.evaluate` an injected
   style: `*{transition:none!important;animation-play-state:paused!important;caret-color:transparent!important}`
   via `document.head.appendChild(style)`. The runtime (T2.2) owns the rest.
6. **Benchmark script** `scripts/bench_scene_capture.py`: renders a static
   test page (`static/scene/_test/static.html`, a title and a box) for 90
   frames at 1920×1080 and at 480×270, prints frames per second achieved.
   Opt-in and labelled heavy.
7. **Tests.** `tests/unit/test_cdp_framing.py`: feed `_Cdp`'s reader a byte
   stream with two concatenated messages and a split one; assert routing by
   id and event capture. No Chromium in unit tests. `tests/visual/test_scene_capture.py`
   (opt-in `YS_VISUAL=1`): render the static test page for 30 frames at
   480×270; assert the mp4 has 30 frames (`ffprobe -count_frames`) and the
   first frame's PNG from `capture_one` is identical to a second call
   (determinism).

## Acceptance
- `capture_one` returns identical bytes on two calls for the static page.
- 30-frame render of the static page produces a valid mp4 with 30 frames.
- Benchmark numbers recorded in the log for this machine at both sizes.
- 3D stage still works: `tests/stage/suite.py` imports and `stage.render`
  (push mode) is unchanged.

## Don't
- No Playwright, no websocket library, no Node. Standard library only.
- Windows: `preexec_fn`/fixed fds are POSIX-only. Do not try to solve
  Windows here; make `_run_cdp` raise `StageError("scene rendering needs
  Linux or macOS for now")` on `win32` and note it in the log. A follow-up
  ticket can add `--remote-debugging-port` with a tiny stdlib websocket
  client.
- Do not change `static/stage/run.js` or the solver.

prototype.*

**Start from `02-scene-engine/reference/cdp_proto.py`.** It is a working,
standard-library-only CDP client over the pipe (`Cdp` class with `send`,
`wait_event` and a reader thread; `launch()` with the correct fd wiring).
It was run against this machine's Chromium 152 (`/usr/bin/chromium`,
Arch) on 2026-10-26 with these results:
```
480x270:   30 frames in 1.62 s = 18.6 fps; repeat capture identical: True; frame 15 == seek(0.5): True
1920x1080: 30 frames in 1.99 s = 15.1 fps; repeat capture identical: True; frame 15 == seek(0.5): True
```
(trivial page: one moving div). So determinism and throughput are proven;
your job is integration. Port `Cdp` into `stage.py` as `_Cdp` and the
`launch()` wiring into `_run_cdp`. Keep the `StageError` on `win32`.

**Things the prototype does not do yet, that you must:**
- Use the existing HTTP server instead of a `data:` URL (`Page.navigate`
  to `http://127.0.0.1:<port>/static/scene/run.html`).
- `Page.navigate` returns before load; `wait_event("Page.loadEventFired")`
  is in the prototype. Clear stale events before each navigate (the event
  list is shared), or you will match the previous page's load.
- Read errors: `Runtime.evaluate` reports page exceptions in
  `result["exceptionDetails"]`, not as a CDP `error`. Check it after every
  `__seek` and raise `StageError` with `exceptionDetails["exception"]["description"]`.
- The reader thread must exit cleanly when Chromium dies (`os.read`
  returns `b""`); make `send()` fail fast then instead of waiting out its
  timeout: put a sentinel in every waiting queue on EOF.

**Encoder.** `_begin()` today is rawvideo+vflip (the 3D page posts GL
pixels upside down). For CDP add `_begin_png(...)`:
`[FFMPEG, "-f", "image2pipe", "-c:v", "png", "-framerate", str(fps), "-i", "-", "-c:v", "libx264", "-preset", "veryfast", "-crf", "12", "-pix_fmt", "yuv420p", "-an", tmp]`.
Note `-framerate` (input option for image2pipe), not `-r`.

**Speed knobs, only if the benchmark disappoints** (record which you
tried): `Page.captureScreenshot {format: "jpeg", quality: 92}` skips PNG
compression in Chromium (ffmpeg then reads `-c:v mjpeg`); or set
`optimizeForSpeed: true` on the PNG call. Do not try
`HeadlessExperimental.beginFrame`: it needs the old headless shell, not
`--headless=new`.

**`deviceScaleFactor`.** Keep the viewport at the composition size
(1920×1080) and set `deviceScaleFactor = size[0] / W`. Verified 2026-10-26:
viewport 1920×1080 with DSF 0.25 gives 480×270 PNGs (19.6 fps on the
trivial page) while CSS layout stays at 1920×1080, which is what proxies
want. Assert the PNG size in the visual test anyway.

**Token for `/scene/<token>/`.** `secrets.token_hex(8)` per `_Run`; in
`translate_path`, reject unless the token matches, then resolve under
`run.job["scene_root"]` and refuse if `Path.resolve()` escapes it.

**Shared flags.** `_chromium_flags(prof, size)` returns the list from
`_run()` minus the URL; `_run()` appends `url`, `_run_cdp()` appends the
pipe flags plus `--mute-audio --hide-scrollbars --force-color-profile=srgb`.
The 3D path's `--use-angle=...` and `--ignore-gpu-blocklist` are harmless
for DOM scenes; keep them shared.
