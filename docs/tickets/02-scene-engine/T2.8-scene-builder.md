# T2.8 Scene builder: layers, motion as data, one compositor
Phase 2 · Size L · Depends on: T2.4, T5.1, T5.2a, T5.2c
*Written 2026-11-01 (Claude Opus 5.5) from the owner's direction: "make an improved
scene builder a priority. We aren't trying to fully recreate Hyperframes, just some of
the capabilities, templates, blocks, and then custom scene creation when appropriate."*

## Goal
One scene builder that every scene uses (templates, blocks, cuts, custom scenes):
Chromium lays out and draws each **layer** once, and ffmpeg does **all** timing and
motion from a small motion vocabulary declared as data. Rendering cost grows with the
number of layers, not the number of frames, and the ffmpeg graph stays bounded however
long the segment is.

## Why
Overly slow rendering is what went wrong with Hyperframes, and Phase 5 repeated it:

| Measured on the owner's project (quarter size, one picture) | Time |
|---|---|
| Essay captions, every frame through CDP (T5.1 round 1) | 96.9 s |
| Essay captions, plates once + ffmpeg (T5.1 committed) | 9.5 s (Pillow 11.7 s) |
| Board, plates once + ffmpeg (T5.2a committed) | 7.3 s (Pillow 17.0 s) |
| Loudmouth, every frame through CDP (T5.3a round 1) | 292.8 s (Pillow 4.6 s) |
| Loudmouth, one ffmpeg node per word (T5.3a round 2) | fails: 383 nodes, 105 KB graph, "Argument list too long" |

The fast pattern works, but each ticket built its own copy (`scenes.caption_plates`,
`board_scenes.render`, `custom_scenes.render`) and the next one got it wrong. This
ticket makes it the engine, once.

**Scope.** Not a Hyperframes clone. We need: templates (our formats and cuts), blocks
(Phase 12), and custom scenes when appropriate (T5.2c/T5.2d, T12.6). No general
timeline editor for scenes, no arbitrary GSAP timelines in final renders.

## Design
1. **Layers.** A template marks each independently timed element with
   `data-layer="<id>"` plus `data-start`, `data-duration`, `data-motion` (preset name)
   and optional `data-motion-*` parameters. Anything without `data-layer` is part of
   the template's static **ground** layer. Layers may nest only one level (a layer's
   children belong to it).
2. **One capture session per segment.** Load the page once at the target size, read
   every layer's box and metadata with a probe, then capture each layer as a cropped
   RGBA PNG (other layers hidden), plus the ground. Cache each PNG by a content key
   (template, layer HTML, computed style inputs, size), so a resume or a repeated
   phrase costs nothing. Capture count = layers + 1.
3. **Motion table as data.** `static/scene/motion.json` defines each preset once
   (from/to for opacity, x, y, scale, wipe; duration default; ease). `runtime.js`
   reads it for the in-app scrub, and `app/scene_builder.py` compiles it to ffmpeg
   overlay/alpha expressions. One table means preview and render cannot drift. Eases
   the compiler supports: linear, quad-out, cubic-out, expo-out, back-out (pop).
   `blur-in` renders as fade + scale in ffmpeg; document the difference.
4. **Camera.** A scene may declare camera keyframes (x, y, zoom over time) in data.
   Compile to one crop/scale per screen on the composited ground, never per layer.
5. **Bounded graphs.** The compiler writes `-filter_complex_script` to a file (never a
   giant argv; ffmpeg 9 uses the equivalent `-/filter_complex` file option).
   Hard cap: 48 moving layers per ffmpeg pass. Beyond that, split the
   segment at **screen boundaries** (the template marks screens with
   `data-screen`; Loudmouth's pages, a board's sheet), render each screen as its own
   pass and concat. Layers whose motion has finished are flattened into the screen's
   ground for later passes, so graph size depends on what moves at once, not on the
   segment length.
6. **Escape hatch.** A layer may set `data-capture="frames"` for motion that ffmpeg
   cannot express (path morphs, particle effects). Only that layer's arrival window is
   captured per frame and overlaid; the template's `budget` (default 10% of the
   segment's frames) is enforced, and over budget is an error naming the layer.
7. **One entry point.** `scene_builder.render(project, template, ctx, out, *, seconds,
   size, fps, crf, extra)` returns the encoded clip. Preview `-vf scale=` in `extra` is
   handled here (plates are drawn at the preview size), replacing `without_scale`.

## Steps
1. Write the design above into `docs/scene-builder.md` (short, with the motion table
   and a template example), and keep it current.
2. Add `static/scene/motion.json`; make `runtime.js` presets read it (behaviour of
   existing presets unchanged).
3. Add `app/scene_builder.py`: probe, layer capture (one session), content-keyed cache,
   motion compiler, camera, screen splitting, script-file graphs, capture-window escape
   hatch, `render(...)`.
4. Add a `stats` result to `render` (captures, cache hits, layers, passes, largest
   graph bytes, captured frames) and log it at debug level.
5. Unit tests with mocked capture: capture count = layers + 1; cache hit on repeat;
   graph bytes stay under 64 KB for a synthetic 20-minute segment with 2,000 layers
   across screens; presets compile to the expected expressions; over-budget capture
   window raises.
6. `tests/visual/test_scene_speed.py` (opt-in with `YS_VISUAL=1`): a synthetic 60 s
   scene with 40 layers, a camera move and one 1 s capture window at 480x270 must
   render in under 3x the time of an ffmpeg-only baseline of the same length, and
   report its stats.

## Don't
- No per-frame CDP capture outside a declared capture window.
- No ffmpeg node per word or per letter; text that arrives word by word is one layer
  with a wipe, or one layer per line, never per word.
- No `-filter_complex` on the command line for generated graphs; use the script file.
- No Node, no build step, no new runtime dependency.
