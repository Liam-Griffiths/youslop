# T20.1 UX self-review of the whole app
Phase 20 · Size M · Depends on: Phase 17, Phase 18, T15.2 · Runs before Phase 19 · Worker: Claude Opus 5.5
*Written 2026-11-11 (Claude Opus 5.5). Owner: "let's add a UX self review section performed by Claude".*

## Goal
Claude uses the real app end to end, the way a new creator would. The
result is two things:
- a review report with screenshots and ranked findings;
- one fix ticket per accepted finding group.

The review itself changes no code.

## Why
Codex builds each ticket against its own acceptance list, and each review
covers one diff. Nobody has gone through the whole studio as one journey
since Phase 9. Seams show up only that way: wording that changes between
stages, dead ends, unclear waits and missing empty states. Doing this before
the website means the screenshots show the fixed app.

## Who and when
- **Claude Opus 5.5 does it, not Codex.** It needs judgement about the whole
  flow and live driving of the browser.
- **It runs after Phase 17, Phase 18 and T15.2, and before Phase 19.**
- **Say before starting.** It uses a lot of Claude usage, and the app plus
  Chromium run for a long time.

## Read first

  checked: principles, tokens, shell, components, screen by screen, and

## Setup
- Work on a fresh `CORKBORED_DATA` temp folder, never the owner's data.
- Run the app from the checkout. Drive it with headless Chromium through
  the existing CDP path at 1440×900. Also do one pass at 1280×720, the
  smallest supported window.
- **Writing model:**
  - use the owner's local LM Studio when it's running (see
    `docs/local-models.md`);
  - otherwise, start the generation journeys from imported projects;
  - never send owner data to a hosted model.
- **Renders:** quarter-size section previews only. Never the whole cut.

## Journeys (screenshot every step)
1. **First run:** setup, choosing models and voices, an empty Home.
2. **Idea to video:**
   - new project from an idea;
   - Plan and sources;
   - Script edits;
   - Voice: record one take with the test tone source if there's no mic,
     and generate text-to-speech for the rest;
   - Visuals: mixed kinds, swapping a picture, adding a block;
   - Edit: the timeline after Phase 17, including undo and inserting;
   - Review & Publish: Check findings, a section preview, the publishing
     screen without uploading.
3. **Bring your own script:** paste a script and follow it through to
   Visuals.
4. **Channels:** create one, pick a style kit, theme the blocks and preview
   them, then start a project in the channel.
5. **Blocks library:** browse, preview, try with your own text, pin.
6. **Footage:** import a short clip, label it, use it.
7. **Settings:** models, voices, speech-to-text engines, paths.
8. **Recovery:**
   - cancel a long job;
   - close and reopen mid-job;
   - a missing model;
   - offline picture search;
   - a deleted file on disk;
   - an invalid paste.

The parked clip screens (Phase 14) get a light pass only: what a user sees
if they wander in.

## What to check at each step
- **Next step:** is it obvious what to do next, and is there one primary
  action?
- **Waiting:** does every wait over a second show progress, and can the user
  leave and come back?
- **Empty, loading, error and disabled states:** does each one say why and
  what to do?
- **Words:** are they the same as in the design guide and the same across
  stages? Is the copy plain, with no hype?
- **Layout:** check alignment and spacing against the tokens, overflow, text
  truncation at 1280×720, and focus order.
- **Keyboard:** can every main action be done from the keyboard? Are there
  visible focus rings and Escape to close?
- **Accessibility:**
  - contrast of text and controls;
  - labelled controls, from Chromium's accessibility tree over CDP;
  - no meaning shown by colour alone.
- **Safety:** can anything lose work? In particular, recorded audio must
  never be lost, and edits must survive a reload.
- **Console:** zero errors and no failed network requests.

## Output
1. **`docs/ux-review/2026-MM-DD/`**, git-ignored apart from `README.md`:
   - `README.md` holds the findings table: id, journey and step, severity
     (P1 blocks or loses work, P2 confuses, P3 polish), what happens, what
     it should do, and a screenshot path;
   - the screenshots go beside it.
2. **The same report published as an artifact**, so the owner can read it
   with the pictures inline.
3. **Fix tickets.** After the owner triages the findings, write T20.2,
   T20.3, … in this folder. Group findings by screen or component, keep
   each ticket under the 600-line diff guideline, and add them to
   `PROGRESS.md` for Codex.
4. **Quick wins.** Copy-only fixes under about 10 lines may be grouped into
   one "copy pass" ticket rather than fixed during the review.

## Acceptance
- All eight journeys were walked, with screenshots for each step and the
  console checked on every screen.
- Every finding has a severity, a screenshot and an expected behaviour.
  P1s are listed first.
- The owner has the artifact link. Fix tickets exist only for findings the
  owner accepted.
- No code changed, the owner's data folders weren't touched, and nothing
  was rendered beyond quarter-size section previews.

## Don't
- Fix things during the review. Write them down.
- Judge against personal taste where the design guide has decided.
  Disagreements with the guide go in a separate "guide questions" list for
  the owner.
- Review the website. It doesn't exist yet at this point.
