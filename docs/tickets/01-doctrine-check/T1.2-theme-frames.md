# T1.2 Theme defaults for frame
Phase 1 · Size S · Depends on: T1.1

## Goal
Each entry in `themes.THEMES` can override FrameSpec fields, and applying a
theme to a channel writes those overrides onto the channel's frame.

## Why
Hyperframes ships twelve premade frames, each with its own pacing and type
scale. Our themes already carry palette and slate templates; they should
carry pacing too, so "Arcade" cuts faster than "Archive" without anyone
editing numbers.

## Read first
- `app/themes.py`: `THEMES`, `palette()`, `apply_to_style()`.
- `app/schema.py`: `FrameSpec` from T1.1.
- Where the UI applies a theme (search `apply_to_style` in `app/main.py`).

## Steps
1. Add an optional `"frame": {...}` dict to each `THEMES` entry. Start with
   two deliberate ones and leave the rest empty:
   - Arcade (or the fastest theme): `montage_cut_max_s 0.5`, `punch_max 1.25`,
     `transition_types ["cut","dip","wipeleft"]`.
   - Archive (or the slowest): `move_max_s 0.8`, `creep_max 1.10`,
     `transition_types ["fade","dip"]`, `shot_avg_min_s 2.5`.
   - Archive is also the default theme; all other themes get empty dicts.
     Keep `FrameSpec()` defaults independent of themes.
2. `apply_to_style(style, key, ...)` mutates style and returns template
   picks. Add a sibling `apply_to_frame(frame: FrameSpec, key) -> FrameSpec`
   that merges the theme's frame dict onto a copy. Call both in the theme
   picker endpoint. Channel creation accepts name/concept/tagline only;
   themes are applied afterward through that endpoint. Leave bare
   `style.theme` patches alone. `new_project` already copies the channel
   frame (T1.1); do not re-apply a theme there.
3. Test `tests/unit/test_themes_frame.py`: applying Arcade changes exactly
   the listed fields; applying a theme with no frame leaves defaults.

## Acceptance
- Creating a channel with the Arcade theme gives it a faster frame.
- Existing channels are untouched until a theme is re-applied.

## Verify
```sh
.venv/bin/pytest tests/unit/test_themes_frame.py -q
```

## Don't
- Do not invent twelve frames. Two deliberate ones; the rest can follow
  from use.

## Implementer notes
*Added 2026-10-26.*

- **Archive is the default theme** ("what every channel made before themes
  existed already looks like"). It is fine to give it the slow overrides,
  because themes only reach a frame when someone applies one (see below), but
  the ticket's "default documentary theme: nothing" is the same entry. Do
  Arcade (fast) and Archive (slow) and leave the rest empty. Do **not** make
  `FrameSpec()` defaults depend on a theme.
- `apply_to_style` **mutates the style in place** and returns the template
  picks, not a dict of changes. Mirror it:
  ```python
  def apply_to_frame(frame: FrameSpec, key: str) -> FrameSpec:
      return frame.merge(theme(key).get("frame") or {})     # T1.1 merge
  ```
- There is one caller: `main.apply_theme` (~line 395,
  `POST /api/channels/{cid}/theme`). Add `ch.frame = themes_mod.apply_to_frame(ch.frame, key)`
  next to `apply_to_style`. Also check channel creation (`new_channel` and
  its endpoint) and the theme branch in `patch_channel`/`patch_project`
  (`style.theme` is set there **without** calling `apply_to_style`; leave
  that path alone so it stays consistent).
- `new_project` does not apply themes; it copies the channel's style. Copy
  the frame the same way (that is T1.1's job); no theme call needed there.
- `themes.py` must not import `schema` at module top if `schema` imports
  `themes` (check; `schema.py` imports nothing from `themes` today, so a
  top-level `from .schema import FrameSpec` is fine).
- `wipeleft` is a real ffmpeg `xfade` transition name; keep the names in
  `transition_types` to ones `xfade` knows (`fade`, `fadeblack`, `wipeleft`,
  `slideleft`, ...) plus our own `cut` and `dip`.
