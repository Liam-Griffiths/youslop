# T19.3 Download and releases pages, and deploy to Vercel or Bunny
Phase 19 · Size S · Depends on: T19.1 · Worker: Claude Opus 5.5
*Written 2026-11-11 (Claude Opus 5.5) from the owner's brief in `README.md`.*

## Goal
The site gains two pages:
- `/download/` picks the right build for the visitor;
- `/releases/` lists every release with its notes and per-platform files.

The static `out/` deploys to either Vercel or a Bunny storage and pull
zone, and binaries are never served from Vercel.

## Why
The owner asked for "a download link (a page with all the releases)". The
binaries are the heaviest thing the site links to, so where they're hosted
decides the bill.

## Read first
- `README-BUILD.md`, for the platforms and archive formats that exist
  (macOS `.app`, Linux and Windows folders).
- The README cost model.
- GitHub Releases on `Liam-Griffiths/youslop`. None existed on 2026-11-11.

## Steps
1. **One release manifest.**
   - `site/content/releases.json` lists, newest first:
     `{version, date, notes_md, files: [{platform, arch, kind, url, size, sha256}]}`.
   - `site/tools/sync_releases.py` (Python, standard library) fills it from
     the GitHub Releases API, using a token from the environment if the repo
     is private.
   - It can also rewrite asset URLs to a Bunny storage base
     (`--asset-base`), for when binaries are mirrored there. It never
     downloads binaries into `site/`.
   - The build reads only the committed JSON, so there is no network at
     build time.
2. **`/download/`**
   - Detect the OS on the client (`navigator.userAgentData`, falling back
     to the UA) to highlight one button.
   - Every platform is listed below it, with size and SHA-256.
   - Show short install notes per platform, taken from `README-BUILD.md`:
     glibc for Linux, the unsigned app for macOS until signing exists.
   - When `releases.json` is empty, say "No release yet. Build from source"
     with the link.
3. **`/releases/`**
   - Every version as a section, with its date, notes rendered from
     markdown at build time, and a file table. The latest is marked.
   - Anchor links per version and a static `releases.xml` Atom feed.
4. **Deploy configs.**
   - `site/vercel.json`:
     - static output;
     - long immutable cache headers for `/_next/static/*`, `/media/*` and
       `/fonts/*`;
     - `"images"` left unset.
   - `site/deploy/bunny.md` and `site/tools/deploy_bunny.py` upload `out/`
     to a storage zone over the Bunny Storage API, with the key from the
     environment.
     - They set the pull zone's cache rules (HTML short, hashed assets a
       year) and purge HTML after upload.
     - Run them only on the owner's instruction.
   - Document the two-host option too: HTML on Vercel and
     `NEXT_PUBLIC_MEDIA_BASE` on Bunny.
5. **Release hook.** Document how a new release reaches the site: run
   `sync_releases.py`, commit, and push, which triggers a Vercel build or
   `deploy_bunny.py`. There is no CI in the repo today, so don't add any
   without asking.

## Acceptance
- `/download/` and `/releases/` render from a sample `releases.json` with
  two versions × three platforms, and from an empty one.
- Headless Chromium checks Windows, macOS and Linux user agents, with 0
  console errors. Each highlights its own platform.
- Every binary link in `out/` points off-site (GitHub or the Bunny base),
  and no file over 2 MB is inside `out/`.
- Nothing is deployed and no DNS is changed without the owner's go-ahead.
  The Log records the preview URL the owner approved.

## Owner decisions (ask before deploying)
- The host: Vercel, Bunny or both.
- The domain (`app/brand.py` `SITE_URL` is `corkbored.com`).
- Whether binaries are mirrored to Bunny or link to GitHub.
- When the repo and its releases become public.

## Don't
- Commit binaries, API keys or tokens.
- Add analytics or download counters.
- Retire `static/landing.html` without the owner's say-so.
